# Feature Specification: CRD Space Settings Page

**Feature Branch**: `045-crd-space-settings`
**Created**: 2026-04-14
**Status**: Draft
**Input**: Migrate the Space Settings area (About, Layout, Community, Subspaces, Templates, Storage, Settings, Account tabs) from the current MUI implementation to the CRD design system (shadcn/ui + Tailwind), following the prototype reference at `prototype/src/app/components/space/SpaceSettings*.tsx`. Related sibling effort: `042-crd-space-page` — the CRD Space Page delivers the space hero (banner / title / tagline / member avatars) and the space-level visual language that this settings area reuses verbatim.

## Clarifications

### Session 2026-04-15

- Q: When CRD is enabled but not every tab has been migrated yet, what should a not-yet-migrated tab show? → A: All 9 tabs ship together in a single release — no progressive rollout and no mixed-shell fallback.
- Q: What happens when the admin switches to another tab while the current tab has unsaved changes? → A: The tab switch is blocked by a CRD confirmation dialog. Only one tab is ever dirty at a time. *(Amended 2026-10-22: the unsaved changes are the ones counted in the tab's unsaved-changes bar — see Session 2026-10-22 and FR-026.)*
- Q: Who can see the Account tab (plan, entitlements)? → A: Visibility mirrors the current MUI Space Admin Account page exactly. No new role gates.
- Q: What is the keyboard alternative to drag-and-drop on the Layout tab? → A: Each movable item's drag handle is focusable. Space/Enter activates grab mode, Arrow Up/Down reorders within the column, Arrow Left/Right moves across columns, Enter drops, Escape cancels. Announced via ARIA live region.

### Session 2026-04-27 — subspace (L1 / L2) settings extension

- Q: Should the CRD Space Settings page also serve subspace (L1) and sub-subspace (L2) admins, or only top-level (L0) spaces? → A: **All three levels**. The settings page is reused for L0 / L1 / L2 with **level-aware tab visibility** mirroring the legacy MUI configuration in `SpaceAdminRouteL0.tsx` / `SpaceAdminRouteL1.tsx` / `SpaceAdminRouteL2.tsx`. The same CRD components, data hooks, and route gate (`NonSpaceAdminRedirect`) are used at every level.
- Q: Tab visibility per level? → A: **L0** — all 9 tabs (about, layout, community, updates, subspaces, templates, storage, settings, account). **L1** — hide templates, storage, account. **L2** — hide templates, storage, account, AND subspaces (sub-subspaces cannot have L3 children).
- Q: ID resolution at L1 / L2? → A: At L1 / L2, `roleSetId` / `communityId` / `guidelinesId` / page URL MUST come from `SubspaceContext` (via `useSubSpace()`), NOT from `SpaceContext` (which is hardcoded to the L0 root). A new `useSettingsScope()` helper resolves the correct IDs based on `useUrlResolver().spaceLevel`.
- Q: Member-lead toggle at L1 / L2? → A: **Add it.** Promote / demote of community members and organizations to / from Lead is currently missing in CRD settings (read-only `roleLabel`). Build the capability generically, but **gate the dropdown items to L1 / L2 only** in this PR. L0 visibility is deferred until a future "hide-state" treatment lands.
- Q: Phase (innovation-flow state) add / delete at L1 / L2? → A: **Add them.** The Layout tab currently allows rename + reorder columns only; phase Add / Delete exists in legacy MUI's `InnovationFlowSettingsDialog`. Wire them via the existing `useInnovationFlowSettings.actions.{createState,deleteState}` for atomic create + sortOrder behaviour. **Gate Add Phase + Delete phase to L1 / L2 only** in this PR (same L0-deferred rationale as the lead toggle).
- Q: Per-tab inner gating that mirrors legacy MUI's `MemberActionsSettings`? → A: **Community tab**: hide "Save as guidelines template" and the Virtual Contributors block at L1 / L2. **Settings tab**: gate four toggles by level — `subspaceAdminInvitations` (L0+L1), `memberCreateSubspaces` (L0+L1), `inheritMembershipRights` (L1+L2), `subspaceEvents` (L0+L1). **Subspaces tab**: hide "Default Subspace Template" card at L1 (template-management is L0-only). **Layout tab**: phase Add / Delete visible only at L1 / L2.
- Q: Authorization gate at L1 / L2? → A: Wrap each subspace settings route in `NonSpaceAdminRedirect`, sourcing the subspace id from `SubspaceContext`. Same redirect pattern legacy MUI uses (`SpaceAdminRouteL1.tsx:75`).
- Q: Breadcrumbs on L1 / L2 settings? → A: When on `/settings`, the subspace name MUST become a link to the subspace home, and the trail MUST append a "Settings" hop (linking to `<subspace>/settings`) plus the active settings tab label. This mirrors the L0 settings breadcrumb shape.

- Q: Can the admin keep rearranging the Layout while it is being written? → A: **No.** While the Layout Save is in flight (`saveBar.kind === 'saving'`), or a tab/phase create/delete or a flow replacement is running, the column buffer is **locked**: no callout or column drag can start (no DnD sensors, every sortable/droppable disabled, drag handles `disabled`) and each row's **Move to…** is disabled. Reason: Save computes its mutations from the buffer as it was when clicked and then marks that buffer clean, so any edit landing mid-save would be silently treated as saved — the UI and server would disagree with no Save button left to reconcile them. The lock lifts when the save settles (`clean` or `saveError`).

### Session 2026-10-22 (Unsaved-changes bar replaces inline saves)

Decided by the product owner after trying the prototype's `SaveBar` (`alkem-io/client-web-prototype` — `shared/SaveBar.tsx`, `shared/UnsavedChangesGuard.tsx`). This session supersedes the per-section Save of Session 2026-10-16, the immediate-commit Settings toggles of FR-023, and the in-page Layout Save / Reset row; see FR-025 – FR-026c.

- Q: How are settings edits saved? → A: **Through one tab-wide unsaved-changes bar** (`SpaceSettingsUnsavedChangesBar` — *renamed `UnsavedChangesBar` and moved to `@/crd/components/common` 2026-10-22, shared with spec 097's Profile tabs*), fixed to the bottom of the viewport like the prototype's `SaveBar`. It appears while the active tab has unsaved changes and shows, left, a filled circle holding the **count** and the text "1 unsaved change" / "N unsaved changes"; right, **Discard** and **Save changes**. Every inline Save (About's per-section `FieldFooter` Save / Saved! / Retry) and every immediate-commit settings control (Settings tab radios and toggles) is replaced by it. **Save changes** saves every change on the tab. The bar is per tab — only one tab can hold unsaved changes at a time (FR-026).
- Q: Which edits go into the bar? → A: **About**: name, tagline, What, Why, Who, city, country, tags, references (including rows whose file was attached through the paperclip — the file upload itself is the existing temporary-upload flow; the row is saved with the bar) and **every Classifications action** — picking values, the show-on-space toggle, adding a classification from a template and removing one (amends workspace spec 024 FR-006a for the CRD client). **Not** the Visuals: avatar / page banner / card banner still commit on file pick through the crop step. **Layout**: the existing buffer (callout drag / Move to / reorder, column reorder). **Settings**: every radio group and toggle (privacy, user-information visibility, membership policy, Trusted Applicants, every Allowed Action).
- Q: What stays immediate? → A: **Actions that are not form fields.** Layout column-menu dialogs and actions (Edit Details, phase layout, default post template, active phase, show / hide, add / delete phase, replace flow); Subspaces sort mode, reorder, pin, create, delete, save as template; Community member / organization / VC actions; Templates and Storage actions; Settings and Account danger-zone deletes and Save as template; Updates posting and removal. The Application Form and Community Guidelines keep their own dialog Save (`SettingsEditorDialog`) — the Community tab never shows the bar.
- Q: What counts as one unsaved change? → A: **Each changed field** — a value that differs from the server; changing it back removes it from the count. About: name, tagline, What, Why, Who, city, country — 1 each; tags — 1 for the whole tag list; references — 1 per added, edited or removed row; classifications — 1 per added or removed classification, plus 1 per existing classification whose values or show-on-space toggle changed. Settings: 1 per radio group or toggle. Layout: 1 per post moved to another column, 1 per column whose post order changed, 1 if the column order changed.
- Q: Does Discard ask first? → A: **Yes.** Discard opens a confirmation ("Discard N unsaved changes?") and on confirm resets every changed field to the server value **in place** — no page reload. Layout's former Reset confirm becomes this shared confirm.
- Q: What feedback does Save give? → A: While saving, the bar shows a spinner + "Saving…" and both buttons are disabled; the tab's editable controls are locked (as Layout already is, Clarification 2026-10-16). On success the bar slides away and a "Changes saved" toast shows. On failure the bar stays with the error in red; the parts that saved leave the count, only the failed ones stay counted, and Save retries them.
- Q: What does leaving a tab with unsaved changes do? → A: **Switching settings tabs** opens the existing confirm dialog (Save / Discard / Cancel); Save there is the bar's Save, and on failure the dialog stays open. **Closing or reloading the browser tab** triggers the browser's `beforeunload` prompt. **Leaving the Settings page through an in-app link** is **not** blocked in this iteration: the app uses `<BrowserRouter>`, which cannot block navigation (`useBlocker` needs a data router). Moving the app to a data router is a separate follow-up story.
- Q: What about Layout actions that reload the board while there are unsaved moves? → A: **Add phase, Delete phase and Replace flow are disabled while the Layout tab has unsaved changes**, with the tooltip "Save or discard your changes first" (Replace flow already was). They reseed the board from the server and would otherwise silently drop unsaved moves.
- Q: Does removing a classification still ask for confirmation? → A: **No.** Removal is staged (counted in the bar) and undone by Discard; nothing is deleted until Save. A classification added and removed before Save simply disappears.
- Q: How does adding a classification from a template work when it is staged? → A: The picked template's values are already on the client (the picker loads them) and value ids are copied verbatim into the snapshot (workspace spec 024 FR-010c), so the new classification renders immediately, marked as unsaved, and its values can be picked before Save. The display-label conflict (spec 024 FR-011a/b) is checked **locally at pick time** against the existing and staged classifications with the same normalisation as the server (trim, collapse whitespace, NFC, case-fold), so the picker's "choose a different label" step still happens at pick time; the server re-checks on Save, and a conflict there fails that classification's save (it stays counted).
- Q: Which About sections are open when the tab loads? → A: **Only Identity.** Visuals, Location, Context, Tags, Classifications and References & Links start collapsed and open on a click of their header; collapsing stays purely visual (the content stays mounted, so collapsed fields keep their edits and still count in the unsaved-changes bar). Supersedes the Session 2026-10-16 "all sections open by default" rule for About; the other tabs' sections are unchanged.

### Session 2026-10-27 (Subspace wording on L1 / L2 settings)

Decided by the product owner after reviewing the subspace settings page, which reused the L0 copy and kept saying "Space" for the subspace being configured.

- Q: On an L1 / L2 settings page, should the copy that names the space being configured say "Subspace"? → A: **Yes.** Every label, hint, placeholder, menu item and dialog text on the settings page that refers to the space being configured says **Subspace** at L1 / L2 ("Subspace Name", "Subspace Members", "Remove from Subspace", "This Subspace is visible…"). Copy that refers to a *different* space keeps "space" and says which one: "the parent space's overview", "All members of the parent space can join directly…", "the top-level space's library". L0 copy is unchanged. FR-042 lists the strings.
- Q: How is the subspace copy selected? → A: With i18next **context**. Each affected key has a `<key>_subspace` sibling in all six locales, and the view passes `{ context: 'subspace' }` when `level !== 'L0'` (at L0 it passes no context and gets the base key). A key without a `_subspace` sibling falls back to the base key. The CRD components that do not take `level` (classification picker and entry card, community guidelines editor, the Customize Sidebar widget list) take a `subspace` boolean prop instead.
- Q: The classification picker at L1 / L2 says "This Space's library" — which library is it? → A: A subspace has no classification library of its own: the picker reads the **top-level (L0) Space's** Template Library (workspace spec 024 FR-007a). ### User Story 2 - Layout tab (Priority: P1)

A space admin opens the Layout tab to organize the space's **callouts / posts** (created by members) across the space's **innovation-flow states** (each state is a column on the Layout board). The number of columns and their names come from the backend (`innovationFlow.states`); admins rename columns in place. The prototype's "Home / Community / Subspaces / Knowledge" labels are example names — a real space may have 3, 5, or any number of columns with user-defined names like "Discover", "Ideate", "Prototype". Columns render side-by-side on desktop and stack on narrow viewports.

Each column card header shows exactly two pieces of content: an **inline-editable title** and an **inline-editable description** (the column represents the space's innovation-flow state). The header has **no icon**, ~~**no callout-count badge**~~ *(amended 2026-10-16: a read-only post-count badge sits before the ⋯ menu, and small pencils beside the title/description open the Edit Details dialog — see Clarifications 2026-10-16)*, and **no collapse / expand affordance**, **and no create / delete / reorder-column affordance** (parity with the current MUI admin, which doesn't surface those either). In the top-right of the header sits a **three-dot overflow menu** that opens the column's action menu — see FR-010. Below the header, the callouts currently assigned to that state are listed with grab handles for drag-reorder (within a column) and drag-move (between columns). Every callout is draggable; the backend does not model pinned / system entries.

**Inline-edit hover pattern** (applies to every inline-editable field across Space Settings — Layout column title, Layout column description~~, any About-tab value rendered without a visible input wrapper~~ *(amended 2026-10-16: About has no inline-edit fields — all boxed inputs)*): the value renders as plain text by default; on hover, the text gains a subtle **underline** and a **small pencil icon** appears trailing the text; clicking either the text or the pencil enters edit mode. The pattern matches the prototype's Home-tab title affordance and must be identical across all inline-editable fields in CRD Space Settings.

Individual callouts are **not** inline-edited from the Layout tab. Their title is rendered read-only as it is in the current MUI implementation; editing a post's own text happens wherever the post normally lives (post page / callout editor). The Layout tab's per-callout actions are limited to **move** and **view** (FR-007).

Moving callouts never triggers a mutation directly. Every change is buffered locally. ~~A sticky Save Changes / Reset action bar at the bottom-right appears when the buffer is dirty.~~ *(Amended 2026-10-22: the shared unsaved-changes bar (FR-025), fixed to the bottom of the viewport, appears when the buffer is dirty and counts the changes per FR-025b; Reset is now its confirmed **Discard**.)* **Save Changes** commits all pending column renames + descriptions, callout moves, callout reorders within a column, and the display-mode toggle to the backend in one go. **Reset** reverts the entire buffer to the last known backend state, discarding unsaved changes. While the buffer is dirty, **Add phase**, **Delete phase** and **Replace flow** are disabled with the tooltip "Save or discard your changes first" *(added 2026-10-22 — they reseed the board from the server and would silently drop the unsaved moves)*.

Each callout row also exposes a three-dot **per-callout menu** with exactly two entries: **Move to** (submenu listing the other columns on the current board — equivalent to drag-and-drop but keyboard-first and without needing to target a drop zone) and **View Post** (navigates to that callout's page — if the Layout tab is dirty, the existing discard-confirm dialog blocks the navigation per FR-026). Move to is buffered like any other layout change; View Post is immediate navigation. **"Remove from Tab" is NOT in this menu** — the backend does not model an "unassigned" state, so a callout always belongs to exactly one column. Deleting a callout happens from the post's own page.

**Zero-mutations-until-Save invariant.** No drag, keyboard move, column rename, Move-to, or display-mode toggle fires any GraphQL mutation before the admin clicks Save Changes. Every change lives in the local buffer only. If the admin clicks Reset, closes the browser tab, refreshes, navigates away (and picks "Discard & leave" in the confirm dialog), or loses their network — nothing has happened on the server.

**Column rename cascade.** Because the backend links callouts to states by `displayName` string (not FK), renaming a column requires cascading the rename to every callout tagged with the old name. The existing `useInnovationFlowSettings` hook performs this cascade today; the CRD `useLayoutTabData` replicates the same pattern inside its Save Changes flow so renames stay consistent.

The Layout tab also includes a **Post description display** toggle (collapsed / expanded). This setting already exists in the current MUI implementation under Settings → Collaboration (via `calloutDescriptionDisplayMode`); in CRD it moves back to the Layout tab because it controls how callouts render.

- **Expanded** (`calloutDescriptionDisplayMode = EXPANDED`) — the callout's full description renders in place on the Space page.
- **Collapsed** (`calloutDescriptionDisplayMode = COLLAPSED`) — the description is truncated (first ~3 lines) with a "Read more" link that expands it inline on click.

The toggle on Layout is a single switch labeled "Collapse post descriptions by default. When enabled, descriptions show a 'Read more' link instead of the full text." — same copy as the current MUI implementation.

**Per-column overflow menu** — each column header's top-right three-dot button opens a dropdown with the same actions the current MUI Layout page exposes per innovation-flow step: **Active phase** (pick the phase this column / step represents) and **Default post template** (pick the default template used when a new callout is created in this column). These are column-level (innovation-flow-step-level) concerns, not per-callout. Selecting an entry fires its mutation immediately (not buffered) — Active phase and Default post template are not part of Save Changes.

The Layout tab never allows creating new callouts, deleting callouts, unassigning callouts, editing a callout's title or description, or creating / deleting / reordering columns. Callouts are created, deleted, and textually edited elsewhere (existing product flows). Column creation / deletion / reordering is not exposed in the current MUI admin either, so CRD matches that.

**Independent Test**: Open Layout. Drag a callout from one column to another. Do not save. Confirm the unsaved-changes bar shows "1 unsaved change" and that Add phase / Delete phase / Replace flow are disabled. Click Discard and confirm — the callout returns *(amended 2026-10-22: was "the action bar shows dirty state … Click Reset")*. Drag again, rename a column title inline, toggle Post description display, click Save Changes. Reload — every change persists.

**Acceptance Scenarios**:

1. **Given** the admin opens the Layout tab, **When** the page renders, **Then** one column card per innovation-flow state is shown (count and names come from the backend), each with an inline-editable title, an inline-editable description, a top-right three-dot overflow menu, and the list of assigned callouts below — no icon, no callout-count badge, no collapse arrow, no create-column affordance, no delete-column affordance, no column-reorder affordance.

3. **Given** the admin drags a callout across columns, **When** they drop it on a valid target, **Then** the callout moves in the local buffer and the action bar appears.
4. **Given** the admin views a callout row, **When** they look for an inline-edit affordance on the post's title or description, **Then** NONE is present — post title and description are rendered read-only on the Layout tab (editing happens from the post's own page).
5. **Given** the admin inline-edits a column's title or description, **When** they confirm, **Then** the edit is held in the local buffer and the action bar appears.
6. **Given** the admin toggles the Post description display setting, **When** they toggle, **Then** the change is held in the local buffer and the action bar appears.
7. **Given** the admin clicks Save Changes, **When** the mutations succeed, **Then** all buffered changes persist in a single logical commit — including any column rename cascading to every callout tagged with the old name — and the action bar disappears. *(Amended 2026-10-22: "the action bar" is the shared unsaved-changes bar; a "Changes saved" toast shows.)*
8. **Given** the admin clicks Reset, **When** confirmed, **Then** the entire buffer is discarded and the UI reverts to the last known backend state. *(Amended 2026-10-22: Reset is the bar's Discard.)*
8a. *(Added 2026-10-22)* **Given** the Layout buffer is dirty, **When** the admin looks at Add phase, a column's Delete phase or Replace flow, **Then** they are disabled with the tooltip "Save or discard your changes first"; **When** the buffer is clean again, **Then** they are enabled.

### Edge Cases

- What happens when an admin opens Space Settings but does not have admin permission for the space? → Same access rules as the current MUI page; unauthorized path is preserved.
- Save mutation fails (any tab with mutations)? → Action bar stays visible, form retains dirty state, inline error banner in the affected card. - Two browser tabs edit the same space simultaneously? → Last save wins; conflicting tab surfaces an inline "Reload current values / Discard my changes" choice on its next save attempt.
- Admin navigates to `…/settings/unknown-tab`? → Tab strip defaults to About and the URL is normalized.
- Empty input that a server rejects (e.g., empty column title on Layout)? → Inline validation prevents save; Save Changes button is disabled while any edit is invalid.
- Dragging across columns violates a backend rule? → The drop is rejected visually, the callout snaps back, and a brief inline message explains why. (The backend currently accepts any cross-column move — this branch is a safety net for future restrictions.)

### Key Entities

- **Space**: The space being administered. Provides the identity fields rendered in the hero and edited on the About tab, plus every tab's data source.
- **Callout / post**: A user-created content item that lives on one of the four space-level tabs (Home / Community / Subspaces / Knowledge). Movable and renamable from the Layout tab; never created or deleted there.
- **Space-level tab column** (Layout): Home, Community, Subspaces, Knowledge. Each has an inline-editable title and description.
- **Space navigation buffer** (Layout): Client-side dirty state that collects pending column-moves, reorders, title edits, description edits, and the `calloutDescriptionDisplayMode` toggle until the admin clicks Save Changes or Reset.
- **Tab unsaved-changes buffer** *(added 2026-10-22)*: The per-tab local state behind the unsaved-changes bar — About's form values, references and staged classification adds / removes / selections / toggles; Settings' privacy, membership and allowed-action values; Layout's navigation buffer. Each exposes its unsaved-change count (FR-025b), a save-all and a reset-to-server, so the bar and the tab-switch dialog drive every tab the same way.
- **Subspace**: A child space. Listed on the Subspaces tab; the same permission model as today; archive state available via `SpaceVisibility.Archived`.
- **Template**: A reusable artifact of category Space / Collaboration Tool / Whiteboard / Post / Community Guidelines.
- **Document**: A file in the space's storage tree.
- **Community member / lead**: An identity (user, organization, or virtual contributor) with a role in the space.
- **Space privacy / visibility / allowed-actions settings**: The configuration values edited on the Settings tab.
- **Space license / entitlements**: The read-only plan information shown on the Account tab.

### Related Specifications

- **042-crd-space-page**: Sibling CRD migration that delivered the CRD Space Page, including the space hero and the visual language for space-level surfaces. This spec reuses that hero verbatim and inherits the same CRD primitives, card patterns, and tab conventions.

### Out of Scope

- Backend / GraphQL schema changes — existing space admin queries and mutations are reused as-is.
- The Communication admin area (current `SpaceAdminCommunication`) is out of scope for the 8-tab redesign.
- New admin capabilities — no new permissions, fields, or configuration options are introduced.
- Platform-level (Global Administration) screens.
- Subspaces: "Edit Details" and "Archive" kebab entries are deferred pending designer review.
- Subspaces: reordering / drag-sort is NOT in scope (not present in the current UI as the user perceives it).
- L0 visibility for the member-lead toggle (FR-037) and the Layout phase Add / Delete actions (FR-038 / FR-039) is **deferred** until a future "hide-state" feature lands. Both capabilities are built generically but gated to L1 / L2 in this iteration.
